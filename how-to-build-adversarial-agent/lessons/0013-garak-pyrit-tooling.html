Open-Source Adversarial Tooling — garak and PyRIT in Practice

🕑 ~30 minutes Practical Implementation
Primary Sources
  • NVIDIA garak — a CLI-based LLM vulnerability scanner covering hallucination, data leakage, prompt injection, jailbreaks, DAN prompts, toxicity, and misinformation, with YAML-driven configuration and support for OpenAI, Hugging Face, AWS Bedrock, Groq, Ollama, and Azure OpenAI providers.
  • Microsoft PyRIT — Python Risk Identification Tool for Generative AI — a Python framework for building custom adversarial testing pipelines composed of five interoperable components (Targets, Attack Strategies, Scorers, Converters, Orchestrators) designed for pre-deployment adversarial assessment of production generative AI systems.

1. garak — The nmap for AI Systems

garak is a CLI-based LLM vulnerability scanner developed by NVIDIA. Its creators describe it using a precise analogy: garak is to AI systems what nmap is to network security. In network security, nmap is the standard tool for scanning a host’s exposed services and identifying potential vulnerabilities. An operator points nmap at a target, waits for the scan to complete, and receives a structured report of findings. garak works in precisely the same way, but the “ports” being probed are the behavioural failure modes of a language model — its tendency to hallucinate facts, leak memorised training data, comply with jailbreak instructions, or produce toxic output.

This design philosophy — automated, repeatable, and structured — makes garak well suited for the pre-deployment stage of an LLM development cycle. Rather than relying on ad hoc manual testing, an engineering team can run garak against a candidate model and receive a per-probe pass/fail report with concrete examples of failures. Just as a network security team would not ship a product with high-risk ports flagged by nmap, an AI team using garak can gate deployment on probe-pass thresholds.

garak supports multiple providers out of the box: OpenAI, Hugging Face models, AWS Bedrock, Groq, Ollama for local inference, and Azure OpenAI. This broad provider support means the same scan configuration can be run against a commercial API or a locally-hosted model without code changes, making it a versatile tool for comparative evaluation across model versions and deployment environments.

2. garak Probe Categories — Seven Classes of LLM Failure

garak organises its test cases into seven broad probe categories, each targeting a distinct class of LLM failure mode.

Hallucination probes test whether the model generates false factual claims with apparent confidence — for instance, inventing plausible-sounding but nonexistent package names. Hallucination is one of the most commercially significant failure modes, as it can mislead users who treat model outputs as authoritative.

Data leakage probes test whether the model reproduces memorised content from its training set. A model that regurgitates verbatim copyrighted text, personal data, or confidential system prompts poses both privacy and legal risks.

Prompt injection probes test whether the model can be hijacked by adversarial instructions embedded in its input. A successful injection overrides the legitimate operator’s system prompt, turning the model into a tool for the attacker.

Jailbreak probes test whether the model complies with requests it should refuse when those requests are framed using known jailbreak patterns. Closely related are DAN — “Do Anything Now” — probes, which target a historically prominent family of jailbreak instructions designed to convince a model to operate outside its safety constraints.

Toxicity generation probes test whether the model can be induced to produce harmful, hateful, or harassing content. Misinformation generation probes test whether the model will generate and present false claims as factual.

3. Attack Methods and YAML Configuration in garak

garak implements three types of attack methods that determine how probe strings are generated and delivered to the target model. Static attacks use pre-written, fixed probe strings assembled into a library: they are fast to execute and fully reproducible, but they cover only known vulnerability patterns present in garak’s probe library. Dynamic attacks generate probe strings at runtime, typically using templates or parametric variation, allowing coverage to scale beyond the static library without requiring manual authorship of every variant. Adaptive attacks go further by evolving probe content based on the model’s own responses: if an initial probe fails to elicit a policy violation, an adaptive strategy can modify the payload in reaction to what the model actually said, mimicking the iterative refinement a human red-teamer would apply.

Configuration is driven by YAML files structured around three main blocks. The generator block specifies the model provider, model name, and any endpoint parameters required to reach the target — such as a local Ollama server running on port 11434. The probes block lists the probe classes to execute, referenced by their garak class names, for example promptinjection.DirectInjection or hallucination.PackageHallucination. An optional detectors block allows operators to override default success-detection logic for individual probes: an operator can specify a custom string that, if found anywhere in the model’s output, should be flagged as evidence of a successful attack.

The final output is a structured report listing per-probe pass/fail rates together with examples of the specific model responses that triggered each failure — directly analogous to a network vulnerability scan report, and interpretable by security teams already familiar with that format.

4. Microsoft PyRIT — A Programmatic Adversarial Framework

Where garak provides a CLI-driven scanning experience, Microsoft’s Python Risk Identification Tool for Generative AI — PyRIT — takes a fundamentally different approach: it is a Python framework rather than a standalone CLI tool, designed to give security professionals and AI red-teamers full programmatic control over how adversarial pipelines are constructed and executed.

PyRIT’s primary use case is pre-deployment adversarial assessment for generative AI systems in production. Unlike garak’s fixed probe library, PyRIT allows practitioners to build custom attack sequences tailored to the specific application under test — including multi-turn conversation attacks where the adversarial strategy adapts across several exchanges. This level of control is necessary when the attack surface is application-specific and cannot be fully covered by a generic probe library.

PyRIT integrates natively with Azure AI services, reflecting its origin as a Microsoft internal tool that was subsequently open-sourced. Teams building on the Azure AI stack can target Azure OpenAI deployments directly using PyRIT’s built-in integrations. However, the framework’s architecture is general enough to wrap any AI system that can be accessed through a Python interface, making it usable beyond the Azure ecosystem.

In practice, garak and PyRIT serve complementary roles. garak excels at broad automated scanning — running many known probes quickly to flag which vulnerability classes warrant attention. PyRIT excels at deep, targeted assessment — building precisely controlled attack sequences for the specific failure modes that matter for a given deployment context.

5. PyRIT’s Five Core Components

PyRIT’s architecture is built around five interoperable core components that together implement a complete adversarial testing pipeline.

Targets represent the AI system under test. A target wraps the interface to the model being assessed — whether an Azure OpenAI deployment, a local model endpoint, or any other generative AI service — and exposes a uniform interface that the rest of the pipeline can use regardless of the underlying provider.

Attack strategies define how adversarial inputs are constructed. These include single-turn prompt templates and multi-turn conversation patterns that guide an orchestrator through a sequence of exchanges designed to progressively weaken the target model’s safety constraints.

Scorers determine whether an attack succeeded. PyRIT supports string-match scorers — which flag outputs containing specific strings as successes or failures — and LLM-judge scorers, which use a separate language model to evaluate whether the target’s output violates a specified policy. LLM-judge scorers are more flexible and can detect nuanced policy violations that string matching would miss.

Converters transform attack payloads before delivery. Examples include translating a prompt to another language, encoding it in Base64, or introducing surface noise. Converters test whether a target’s safety measures are robust to superficial payload transformations.

Orchestrators coordinate the entire multi-turn attack sequence — feeding converted payloads to the target through the chosen attack strategy, passing responses to scorers, and deciding how to proceed based on each score. The orchestrator is the control loop that transforms individual components into a coherent end-to-end red-team pipeline.

Key Insight: garak and PyRIT represent two distinct philosophies for adversarial LLM testing that address different stages of the same problem. garak offers breadth — a fixed, auditable probe library that any team can run in minutes to detect known vulnerability classes. PyRIT offers depth — a programmable framework for constructing exactly the multi-turn adversarial harness that a specific production application requires. The sharpest red-team programmes use both: garak as a fast gate on every model checkpoint, and PyRIT for the deeper, application-specific assessment that shipping to production demands.
Common Misconception: Running garak’s full probe suite and receiving high pass rates is not equivalent to a comprehensive safety evaluation. garak’s probes target known vulnerability patterns; a model that passes every built-in probe may still be susceptible to novel attack vectors not yet represented in the library. Similarly, PyRIT’s string-match scorers can produce both false positives (flagging benign outputs that happen to match the pattern) and false negatives (missing subtle policy violations that do not match the pattern). Neither tool replaces the human judgment required to design application-appropriate attack strategies and interpret results in context.
