Three Hard Structural Problems in Loop Design

~25 min Module 4 — Failure Modes and Robust Design

Primary Source

Lilian Weng — LLM Powered Autonomous Agents (2023)

The seminal survey of LLM agent architectures identifies three structural challenges that affect every loop: finite context limits historical awareness, LLMs struggle with long-horizon replanning when early errors compound, and natural language interface fragility requires significant output-parsing code. Each challenge has a direct architectural response.

Why These Problems Are Structural

The failure taxonomy in Lesson 10 catalogued what goes wrong inside a loop — bad tool calls, invalid plans, runaway iterations. This lesson steps back to a different level: three challenges that are not implementation bugs but structural properties of LLM-based loops themselves.

Lilian Weng's 2023 survey of LLM agent architectures names these three as the hardest problems in loop design because they cannot be fixed by writing better prompts or choosing a better model. They arise from the way transformers process sequences and the way natural language is used as an interface between the loop's components. Understanding them changes how you design loops from the start.

Problem 1: Finite Context Limits

Every LLM operates within a bounded context window. In a loop that runs for many iterations — research tasks, multi-day planning, long customer conversations — early observations, decisions, and tool results eventually scroll out of the model's active window. Once lost, they cannot be recovered within that run.

This creates an asymmetry: a human operator reviewing the same task retains full memory of what happened in step 1 when working on step 50. The LLM does not. As Weng identifies, finite context limits historical awareness in long loops, making state management a first-class design concern rather than an afterthought.

The design response is external memory. The cheapest form is a rolling summary: when the message list grows beyond a threshold, compress older messages into a summary field and discard them from the active window, keeping only the most recent exchanges in full. A more capable approach stores embeddings in a vector store and retrieves the most relevant past context on demand. Both strategies trade some fidelity for the ability to operate across arbitrarily long horizons without hitting the context ceiling.

Problem 2: Long-Horizon Planning Degradation

LLMs struggle to adapt when unexpected errors arise mid-plan, because they were not trained to recover from compounding mistakes. In short loops — two or three steps — an early error is noticeable and the model can course-correct. In long-horizon plans, an early wrong assumption can propagate silently through subsequent steps until the accumulated error is too large to fix without restarting from the beginning.

The Reflexion architecture documented in Weng's survey addresses part of this: after each action, the agent evaluates its trajectory and can restart if it detects failure — for example, when repeated identical actions produce identical observations with no progress. But Reflexion's detection relies on the agent recognising that it is stuck. Silent degradation — where each step is individually plausible but the overall direction has drifted — is harder to catch.

The design response is checkpointing combined with explicit replanning triggers. Persisting full state at every node means any failure can resume from where it stopped rather than restarting from scratch. Adding a periodic replan check every N steps forces the loop to ask whether the original plan still reflects the current situation, before errors compound further. The trigger is proactive: even if no individual step has failed, drift is detected by comparing the plan against updated context at regular intervals.

Problem 3: Natural Language Interface Fragility

The interface between loop components — between the planner and the executor, between the agent and its tools — is natural language. Natural language is expressive but not precise: a model might return a JSON object with keys in the wrong case, wrap a list in prose instead of brackets, or emit a number as a word. Every divergence from the expected format requires output-parsing code to handle. As Weng identifies, formatting errors and non-compliance require significant output-parsing code across real agent deployments.

This fragility compounds across a loop. If the planner's output needs to be parsed before execution, every malformed response either aborts the step or requires a fallback heuristic. Robust fallbacks are themselves fragile — they work for the cases you anticipated, and fail silently on the ones you did not.

The design response is structured output formats. Using a library like Pydantic to define an explicit schema for the model's output, and invoking the model with llm.with_structured_output(PydanticModel), replaces free-form string parsing with schema-validated, typed objects. The model retries automatically on schema mismatch. This moves the contract between loop components from an implicit natural language convention to an explicit, machine-checkable type definition — and eliminates the class of parsing failures that would otherwise accumulate across a long run.

Key Insight

Each of the three hard problems points to a different boundary in the loop: the context boundary (what the model can see), the time boundary (how far ahead it can reliably plan), and the interface boundary (how reliably components can exchange structured information). Architectural mitigations — external memory, checkpointing with replanning, and structured output formats — address these three boundaries directly, not the surface symptoms.

Watch Out

Treating these three challenges as prompt engineering problems leads to brittle fixes. Adding "remember everything from the beginning" to a system prompt does not expand the context window; it consumes tokens that could hold actual history. Adding "always return valid JSON" does not prevent schema drift; only structured output enforcement at the API level reliably catches it. The mitigations work because they operate at the architectural level, not the instruction level.

LangGraph Implementation

The code below demonstrates all three mitigations in a single graph: a rolling summary node compresses old messages to stay within context limits, a periodic replan check fires every five steps to catch long-horizon drift, and llm.with_structured_output(NextStep) enforces a typed Pydantic schema on planner output so no free-form string parsing is needed. A MemorySaver checkpointer persists full state at every node so any interruption can resume mid-task.

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver
from langchain_anthropic import ChatAnthropic
from langchain_core.messages import HumanMessage, SystemMessage, BaseMessage
from pydantic import BaseModel
from typing import TypedDict, Annotated
import operator

llm = ChatAnthropic(model="claude-sonnet-5")

# ── Mitigation 1: finite context — rolling summary ────────────────────────────
class SummaryState(TypedDict):
    messages: Annotated[list[BaseMessage], operator.add]
    summary: str   # compressed long-term memory

def maybe_summarize(state: SummaryState) -> dict:
    if len(state["messages"]) > 10:
        compressed = llm.invoke(
            [HumanMessage(f"Summarize this conversation history in 3 bullet points:\n{state['messages'][:-4]}")]
        ).content
        return {"summary": compressed, "messages": state["messages"][-4:]}  # keep last 4 messages
    return {}

def respond(state: SummaryState) -> dict:
    context = [SystemMessage(f"Prior context:\n{state['summary']}")] if state["summary"] else []
    return {"messages": [llm.invoke(context + state["messages"])]}

# ── Mitigation 2: long-horizon degradation — periodic replan ─────────────────
class LongPlanState(TypedDict):
    task: str
    plan: list[str]
    step: int

def check_and_replan(state: LongPlanState) -> dict:
    if state["step"] > 0 and state["step"] % 5 == 0:
        verdict = llm.invoke(
            f"Is this plan still valid at step {state['step']}? Reply YES or NO.\n"
            f"Task: {state['task']}\nPlan: {state['plan']}"
        ).content.strip()
        if verdict.startswith("NO"):
            new_plan_text = llm.invoke(f"Replan from step {state['step']}: {state['task']}").content
            return {"plan": new_plan_text.split("\n")}
    return {}

# ── Mitigation 3: NL fragility — structured output via Pydantic ───────────────
class NextStep(BaseModel):
    action: str
    tool: str
    args: dict
    rationale: str

structured_llm = llm.with_structured_output(NextStep)

def plan_next(task: str, context: str) -> NextStep:
    # Returns a validated NextStep object — never a free-form string to parse
    return structured_llm.invoke(f"Plan the next step.\nTask: {task}\nContext: {context}")

# ── Wire up with checkpointing so restarts resume mid-task ───────────────────
checkpointer = MemorySaver()
builder = StateGraph(SummaryState)
builder.add_node("maybe_summarize", maybe_summarize)
builder.add_node("respond", respond)
builder.set_entry_point("maybe_summarize")
builder.add_edge("maybe_summarize", "respond")
builder.add_edge("respond", END)

app = builder.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "long-task-1"}}
# State is persisted at every node — any interrupt restores full context on resume
app.invoke({"messages": [HumanMessage("Start the analysis.")], "summary": ""}, config=config)
