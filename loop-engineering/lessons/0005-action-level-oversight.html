Designing Oversight at the Action Level

~20 min Module 2 — Human Oversight
Primary Source

Chip Huyen — Agents (2025) + Anthropic — Building Effective Agents

Huyen frames human oversight as a continuum where humans can intervene at any stage — providing plans, validating them, or approving risky operations. The key design principle is defining automation level per action type, not per system.

Per-Action Autonomy: Beyond System-Level Settings

Lesson 4 introduced the HITL spectrum as a way to classify entire systems — fully manual, supervised, or fully autonomous. This lesson shifts the unit of analysis from system to action.

Chip Huyen argues that the most practical way to implement oversight is not to pick a single autonomy level for an agent system and apply it uniformly. Instead, automation level should be defined per action type. A single agent might run hundreds of read-only lookups autonomously while still pausing for explicit human approval before deleting a record or sending an email.

This per-action framing is the design principle that makes the HITL spectrum actionable at the architecture level. Rather than asking "how autonomous is this system?", the useful question becomes "how autonomous is each specific action this system takes?"

Reversibility and Consequence Severity

Two dimensions determine where any given action falls on the oversight spectrum: reversibility and consequence severity.

Reversibility asks whether the action can be undone if the agent made an error. Reading a file is fully reversible — no state changes. Sending an email or deleting a database record is not reversible: the action cannot be recalled once executed.

Consequence severity asks how much damage an incorrect execution causes. Querying an API may be technically reversible but if it triggers a billing charge or an external side effect, its effective severity may be medium or high regardless.

Together, these two dimensions produce a policy table that can be evaluated at runtime. Actions that are both reversible and low-severity — such as reading a file — flow straight to execution with no human pause. Actions that are irreversible or high-severity — such as sending email or deleting a record — trigger a checkpoint before the agent is allowed to proceed.

The Intern Analogy

Chip Huyen grounds the severity-based rule in a concrete analogy: "Just as you shouldn't give an intern the authority to delete your production database, you shouldn't allow an unreliable AI to initiate bank transfers."

The analogy captures two things at once. First, it establishes that capability and authorization are distinct — an agent (or an intern) may be technically capable of executing an action while still lacking the organizational trust required to do so autonomously. Second, it establishes that the appropriate level of oversight scales with the consequence of error, not merely the competence of the actor.

A senior engineer can delete a production database because trust has been established through a track record. An AI agent earns equivalent trust through demonstrated reliability over time — not by default at deployment. Until that track record exists, the safe default is to gate actions proportional to their consequences.

Placing Checkpoints in Your Loop

Anthropic's guidance on checkpoint placement is direct: build human checkpoints at natural pause points within the agentic loop, particularly before irreversible actions and when the agent encounters ambiguity or blockers it cannot resolve on its own.

Critically, this is framed as a design choice in the loop's stopping conditions — not an external add-on bolted on after the fact. Checkpoints are first-class citizens of the loop architecture. The practical workflow is: identify which steps in your loop are irreversible, then place human-in-the-loop gates before those steps.

Anthropic further recommends that well-designed agent systems should request only the permissions they actually need, prefer reversible actions where equivalent alternatives exist, and err toward doing less and confirming with users when uncertain about intended scope. A reversibility and severity matrix operationalizes this recommendation directly in code.

Key Insight Oversight is a property of actions, not of systems. The same agent can execute low-risk actions fully autonomously while requiring explicit human approval for irreversible or high-severity steps — setting oversight per action type prevents both over-restriction of routine work and under-protection of consequential operations.
Watch Out Setting a single oversight level for an entire agent system is a common design mistake. Applied uniformly, a conservative setting creates unnecessary friction on every low-risk action; a permissive setting leaves high-severity actions unchecked. Per-action policy takes more upfront design work but avoids both failure modes.

LangGraph Implementation

The gate node checks each incoming action against a policy table keyed on reversibility and consequence severity — only actions that fail the policy (irreversible or high/critical severity) call interrupt(), so cheap read-only actions like read_file flow straight to execute with no human pause. Add new action types to ACTION_POLICY to extend coverage without changing the graph structure.

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict

ACTION_POLICY = {
    "read_file":     {"reversible": True,  "severity": "low"},
    "write_file":    {"reversible": True,  "severity": "medium"},
    "query_api":     {"reversible": True,  "severity": "medium"},
    "send_email":    {"reversible": False, "severity": "high"},
    "delete_record": {"reversible": False, "severity": "critical"},
}

def needs_gate(action: str) -> bool:
    policy = ACTION_POLICY.get(action, {"reversible": False, "severity": "critical"})
    return not policy["reversible"] or policy["severity"] in ("high", "critical")

class ActionState(TypedDict):
    action: str
    payload: dict
    result: str

def gate(state: ActionState) -> dict:
    if needs_gate(state["action"]):
        policy = ACTION_POLICY.get(state["action"], {})
        answer = interrupt({
            "action": state["action"],
            "severity": policy.get("severity"),
            "reversible": policy.get("reversible"),
            "message": "Irreversible or high-severity — approve?",
        })
        if answer != "yes":
            return {"result": "blocked by oversight gate"}
    return {}

def execute(state: ActionState) -> dict:
    if state.get("result"):
        return {}   # already blocked upstream
    return {"result": f"executed {state['action']}({state['payload']})"}

checkpointer = MemorySaver()
builder = StateGraph(ActionState)
builder.add_node("gate", gate)
builder.add_node("execute", execute)
builder.set_entry_point("gate")
builder.add_edge("gate", "execute")
builder.add_edge("execute", END)

app = builder.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "action-1"}}

# send_email triggers interrupt; read_file flows straight through
app.invoke({"action": "send_email", "payload": {"to": "team@co.com"}, "result": ""}, config=config)
# app.invoke(Command(resume="yes"), config=config)   # to approve
