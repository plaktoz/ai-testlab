The Human-in-the-Loop Spectrum

~20 min Module 2 — Human Oversight

Primary Source

Google Cloud — Human-in-the-Loop: Full Spectrum

The Google Cloud spectrum defines three oversight models — Human-in-the-loop, Human-on-the-loop, and Human-out-of-the-loop — with concrete placement criteria based on decision stakes, model confidence, novelty of inputs, and regulatory requirements.

The Three-Tier Oversight Model

AI systems do not sit at a single fixed point on an autonomy scale — they can be positioned anywhere along a spectrum from full human control to full automation. Google Cloud's framework names three distinct tiers that cover the practical range.

Human-in-the-loop (HITL) means the human actively participates in each decision cycle. Every action or classification passes through a human before it takes effect. The system produces a candidate output; the human reviews, approves, or corrects it; only then does the loop continue. This is the highest-oversight position on the spectrum.

Human-on-the-loop (HOTL) means the system runs autonomously while a human monitors it and retains the ability to intervene. The loop proceeds without waiting for human approval on every step, but the human can pause or override if something looks wrong. This is the middle position — automation with a safety net.

Human-out-of-the-loop (HOOTL) is full automation. The system observes, decides, and acts without any human in the path. This is the lowest-oversight position and is only appropriate when confidence and conditions reliably meet a defined threshold.

Criteria for Placing a System on the Spectrum

The Google Cloud framework provides concrete criteria for deciding where to position a system. The criteria are not arbitrary — each maps to a specific risk or reliability property of the task.

Move toward Human-in-the-loop when:

  • The decision is high-stakes and errors carry serious consequences.
  • The model's confidence score is low, indicating genuine uncertainty.
  • The input is a novel edge case the model has not reliably handled before.
  • Regulatory requirements mandate human sign-off on the output.

Move toward Human-out-of-the-loop when:

  • The task is high-volume and repetitive, making per-item human review impractical.
  • The model demonstrates consistently high confidence across a wide range of inputs.
  • The cost of a missed detection or error is low and correctable.

Human-on-the-loop occupies the middle ground: it is appropriate when volume or speed makes full HITL impractical but the stakes are high enough that a human should remain able to intervene.

Oversight per Action, Not per System

Chip Huyen's analysis of agentic systems adds a critical refinement to the spectrum: oversight level should be defined per action type, not per system as a whole. An agent that is classified as "supervised" does not mean every one of its actions requires supervision — it means that some actions do and others do not, based on their individual properties.

The severity-based rule Huyen introduces is direct: "just as you shouldn't give an intern the authority to delete your production database, you shouldn't allow an unreliable AI to initiate bank transfers." The intern analogy captures exactly what the spectrum is for — not restricting every action the agent takes, but calibrating the level of trust granted to each category of action based on the stakes involved.

Huyen identifies two properties that drive the calibration: reversibility (can the action be undone?) and consequence severity (how bad is it if the action is wrong?). Low-reversibility, high-severity actions — deleting records, sending emails, initiating payments — warrant human-in-the-loop handling even inside an otherwise autonomous system. High-reversibility, low-severity actions — reading files, querying APIs — can safely run without human involvement.

The practical implication is that the same agentic system may simultaneously be human-in-the-loop for one class of action and human-out-of-the-loop for another. Treating oversight as a per-system binary misses this granularity and either over-restricts the system (slowing it down unnecessarily) or under-restricts it (leaving high-severity actions unguarded).

Where to Insert Human Checkpoints in the Loop

Anthropic's guidance on building agentic systems operationalizes the spectrum at the architecture level: human checkpoints belong at natural pause points within the loop, particularly before irreversible actions and when the agent encounters ambiguity it cannot resolve on its own.

The key framing is that checkpoints are a design choice in the loop's stopping conditions, not an external add-on bolted onto an otherwise fully-automated system. Designing checkpoints in from the start means the loop's control flow explicitly accommodates human input — the graph suspends, hands off to the human, and resumes once a decision is made. Designing them in after the fact typically means awkward interruptions that break the loop's state rather than pausing it cleanly.

The practical guidance distills to a two-step process: first, identify which steps in the loop are irreversible; second, place human-in-the-loop gates before those steps. Steps that are fully reversible and low-consequence do not need a gate. Steps that are irreversible or high-consequence should always have one.

Key Insight

Oversight level should be defined per action type, not per system. The same agent can operate human-out-of-the-loop for reading files and human-in-the-loop for deleting records — the spectrum is applied action by action based on reversibility and consequence severity, not as a single system-wide setting.

Watch Out

It is tempting to classify an entire application as "automated" or "supervised" and apply that label uniformly. This flattens the spectrum in a way that is almost always wrong: every real system contains some actions that are safe to automate and others that are not. Applying a single oversight level system-wide either blocks low-risk operations unnecessarily or leaves high-risk operations unguarded.

LangGraph Implementation

The following code demonstrates all three oversight tiers in a single LangGraph graph. A route_oversight conditional edge reads the oversight field from state and dispatches to full_gate (always suspends), supervised_gate (suspends only when confidence falls below 0.75), or execute (runs without interruption). LangGraph's interrupt() suspends execution and hands control back to the caller; MemorySaver persists state across the suspension so the graph resumes from the exact same node after the human responds via Command(resume=...).

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict, Literal

class ReviewState(TypedDict):
    action: str
    confidence: float   # 0.0 – 1.0 model confidence
    oversight: str      # "full" | "supervised" | "autonomous"
    result: str

def route_oversight(state: ReviewState) -> Literal["full_gate", "supervised_gate", "execute"]:
    return {"full": "full_gate", "supervised": "supervised_gate", "autonomous": "execute"}[state["oversight"]]

def full_gate(state: ReviewState) -> dict:
    # Human-in-the-loop: always pause, regardless of confidence
    answer = interrupt({"message": f"Approve '{state['action']}'?"})
    return {"result": "rejected"} if answer != "yes" else {}

def supervised_gate(state: ReviewState) -> dict:
    # Human-on-the-loop: pause only when model is uncertain
    if state["confidence"] < 0.75:
        answer = interrupt({"message": f"Confidence {state['confidence']:.0%} — approve '{state['action']}'?"})
        return {"result": "rejected"} if answer != "yes" else {}
    return {}

def execute(state: ReviewState) -> dict:
    if state.get("result") == "rejected":
        return {}
    return {"result": f"executed: {state['action']}"}

checkpointer = MemorySaver()
builder = StateGraph(ReviewState)
builder.add_node("router", lambda s: s)
builder.add_node("full_gate", full_gate)
builder.add_node("supervised_gate", supervised_gate)
builder.add_node("execute", execute)
builder.set_entry_point("router")
builder.add_conditional_edges("router", route_oversight)
builder.add_edge("full_gate", "execute")
builder.add_edge("supervised_gate", "execute")
builder.add_edge("execute", END)

app = builder.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "review-1"}}

# First invoke pauses at interrupt; resume with:
# app.invoke(Command(resume="yes"), config=config)
app.invoke({"action": "delete_user_data", "confidence": 0.95, "oversight": "full", "result": ""}, config=config)
