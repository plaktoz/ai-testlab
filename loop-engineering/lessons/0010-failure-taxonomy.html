Taxonomy of Agentic Loop Failures

~25 min Module 4 — Failure Modes and Robust Design
Primary Source

Chip Huyen — Agents (2025): Failure Taxonomy

Huyen identifies three failure categories — planning, tool, and efficiency — that together cover every way an agentic loop can break down; the taxonomy is the most complete available and is essential for designing robust loops because you can only guard against failures you have named.

Why a Failure Taxonomy Matters

Agentic loops fail in structured, repeating ways. Without a shared vocabulary for those failures, engineers patch symptoms rather than causes: they add retries where they need validation, or add parallelism where they need tool grounding. Chip Huyen's taxonomy from her 2025 "Agents" analysis organises every identified failure into three categories — planning, tool, and efficiency — each demanding a different class of mitigation. Validation at the plan stage addresses planning failures; grounding and schema enforcement address tool failures; flow analysis and step-count auditing address efficiency failures.

The taxonomy also makes evaluation concrete. Huyen recommends evaluating agents against a dataset of (task, tool inventory) tuples and tracking metrics such as valid plan ratio, plans-per-valid-plan, and invalid tool call frequency. Each metric maps directly onto one of the three failure categories, turning a qualitative failure observation into a number you can trend over time.

Planning Failures

Planning failures occur before any tool is executed — they live in the step where the agent decides what to do and how to do it. Huyen identifies four subtypes:

  • Invalid tool calls: The agent calls a function name that does not exist in its tool registry — a hallucination of the planning component. The tool invocation fails immediately, but the damage is already done: a loop cycle has been consumed on a non-executable step.
  • Correct tool, wrong parameters: The agent identifies the right tool but passes arguments that violate the tool's contract — wrong types, out-of-range values, or missing required fields. The tool exists, but the call is still invalid.
  • Goal failures: The agent solves the wrong task. It produces output that is internally consistent and uses real tools correctly, but the result does not satisfy the user's actual intent. Goal failures are the hardest to detect automatically because no exception is raised.
  • Reflection errors: The agent evaluates its own output and incorrectly concludes the task is complete when it is not. The loop terminates early — not because a stopping condition was met, but because the agent's self-assessment was wrong.

The mitigation for planning failures is validation at the plan stage — checking tool names against the registry, validating parameter schemas before execution, and separating the generate step from the execute step so that invalid plans are rejected before they consume execution budget.

Tool Failures

Tool failures occur at the interface between the agent's natural-language reasoning and the executable environment. Even when the plan is valid, the interaction with a tool can break in three ways:

  • Incorrect output: The tool executes successfully but returns a result that is wrong, stale, or misleading. The agent treats the output as ground truth and builds subsequent steps on a faulty foundation.
  • Translation errors: The agent cannot reliably convert between natural language instructions and the precise command format a tool requires. Formatting errors, encoding mismatches, and non-compliance with the tool's input schema all fall here. Huyen notes these require significant output-parsing code to handle robustly.
  • Missing tools: The agent is given a task that requires a capability that simply does not exist in its tool inventory. No amount of replanning can succeed — the system lacks the instrument the task demands.

The mitigation for tool failures is grounding — using structured output formats, schema validation on tool inputs, and tool documentation that is treated like production code. Huyen's framing from the oversight section applies here too: agent reliability is bounded by tool reliability.

Efficiency Failures

Efficiency failures do not prevent the agent from completing a task — they cause it to complete the task using far more resources than necessary. Two subtypes dominate:

  • Excessive steps: The agent takes more loop iterations than the task requires. Each unnecessary step consumes tokens, latency, and API budget. In long-running loops, excess steps also increase the chance that an early error compounds into a later planning failure.
  • Missed parallelism: The agent executes steps sequentially when those steps were independent and could have been dispatched in parallel. Huyen identifies this as a flow analysis problem — the agent's control flow does not reflect the true dependency structure of the task.

The mitigation for efficiency failures is flow analysis: auditing which steps depend on prior outputs and which are genuinely independent, then restructuring the plan to use parallel execution where the dependency graph permits. Tracking the invalid tool call frequency and plans-per-valid-plan metrics surfaces efficiency regressions before they become cost problems.

Key Insight
Each of the three failure categories — planning, tool, and efficiency — requires a different class of mitigation applied at a different point in the loop: planning failures need validation before execution starts, tool failures need grounding and schema enforcement at the tool interface, and efficiency failures need flow analysis of the dependency structure. Applying the wrong mitigation to a failure type wastes engineering effort without reducing the failure rate.
Watch Out
Reflection errors are the most subtle planning failure because they produce no exception and no visible anomaly — the agent simply concludes it is done when it is not. A loop that terminates early due to a mistaken self-assessment looks identical at the surface to a loop that terminated because the task was genuinely complete. Detecting reflection errors requires evaluating final outputs against the original task intent, not just checking whether the loop exited cleanly.

LangGraph Implementation

The following pattern wraps every tool execution in a structured error-capture block that records each failure with its category, subtype, and a mitigation hint; the routing function also inspects the accumulated error_count to detect runaway error loops — an efficiency failure — and hard-stops before further tokens are consumed.

from langgraph.graph import StateGraph, END
from langchain_anthropic import ChatAnthropic
from langchain_core.messages import HumanMessage, BaseMessage
from langchain_core.tools import tool
from langgraph.prebuilt import ToolNode
from typing import TypedDict, Annotated, Literal
import operator

llm = ChatAnthropic(model="claude-sonnet-5")

@tool
def unreliable_search(query: str) -> str:
    """Search for information — may raise on bad queries."""
    if not query or len(query) < 3:
        raise ValueError(f"Query too short: {query!r}")
    return f"[results for '{query}']"

tools = [unreliable_search]

class DebugState(TypedDict):
    messages: Annotated[list[BaseMessage], operator.add]
    failures: list[dict]
    error_count: int

def agent(state: DebugState) -> dict:
    return {"messages": [llm.bind_tools(tools).invoke(state["messages"])]}

def safe_tools(state: DebugState) -> dict:
    last = state["messages"][-1]
    results, failures, error_count = [], list(state["failures"]), state["error_count"]
    for tc in getattr(last, "tool_calls", []):
        try:
            output = unreliable_search.invoke(tc["args"])
            results.append({"role": "tool", "content": output, "tool_call_id": tc["id"]})
        except Exception as exc:
            error_count += 1
            failures.append({
                "type": "tool_failure",
                "subtype": "incorrect_output",
                "tool": tc["name"],
                "args": tc["args"],
                "error": str(exc),
                "mitigation": "sanitise input before passing to tool",
            })
            results.append({"role": "tool", "content": f"ERROR: {exc}", "tool_call_id": tc["id"]})
    return {"messages": results, "failures": failures, "error_count": error_count}

def route(state: DebugState) -> Literal["safe_tools", "__end__"]:
    if state["error_count"] >= 3:    # efficiency failure: runaway error loop
        return END
    last = state["messages"][-1]
    return "safe_tools" if getattr(last, "tool_calls", None) else END

builder = StateGraph(DebugState)
builder.add_node("agent", agent)
builder.add_node("safe_tools", safe_tools)
builder.set_entry_point("agent")
builder.add_conditional_edges("agent", route)
builder.add_edge("safe_tools", "agent")

app = builder.compile()
result = app.invoke({"messages": [HumanMessage("Search for AI news")], "failures": [], "error_count": 0})
print(f"Failures logged: {result['failures']}")
