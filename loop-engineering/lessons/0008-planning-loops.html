Planning Loops — When Structure Beats Improvisation

~25 min Module 3 — Agentic Loop Patterns
Primary Source

Andrew Ng — Agentic Design Patterns Part 4: Planning  &  Chip Huyen — Agents (2025)

Planning is the pattern where the LLM determines a multi-step sequence at runtime rather than following a predefined workflow. A live demo illustrates dynamic adaptation: when a search API rate-limited, the agent pivoted to Wikipedia without any human intervention.

Planning vs. Chaining — Choosing the Right Architecture

Not every multi-step task requires a planning loop. Anthropic distinguishes between workflows — predefined code paths where steps are fixed at design time — and agents — LLMs that dynamically direct their own process at runtime. The choice between them is not about raw capability; it is about whether the task decomposition is predictable before execution begins.

Andrew Ng makes the decision crisp: planning adds value specifically when task decomposition cannot be specified in advance. If you can enumerate all the steps before any specific task instance arrives, a simpler chaining workflow suffices and will be faster, cheaper, and easier to debug. Reaching for a planning loop when a fixed workflow would do is one of the most common sources of unnecessary complexity in agentic systems.

Dynamic Task Decomposition at Runtime

A planning loop asks the model to produce the step sequence as part of the task itself. Rather than executing a hardcoded path, the LLM reads the task description and generates an ordered list of sub-tasks it will need to complete. Chip Huyen frames this as a search problem: the agent evaluates paths toward a goal using heuristics or AI judges to validate candidate plans before any execution begins.

The rate-limit adaptation example from Ng’s live demo captures what makes planning loops valuable in practice. When a search API returned a rate-limit error mid-task, the agent did not fail — it replanned, substituting Wikipedia as the information source and continuing without human intervention. A hardcoded workflow would have halted at that point. The planning loop adapted because it treated its own plan as a revisable artifact, not as fixed instructions.

The Plan → Validate → Execute Cycle

Huyen’s decoupling principle structures the planning loop into three distinct phases that should never be collapsed into one. First, generate a plan: the LLM decomposes the task into an ordered list of steps given the available tool inventory. Second, validate the plan: a separate validation pass — a heuristic check or a second LLM call — confirms the plan is complete and uses only available tools before any execution begins. Third, execute step by step: each step runs in sequence, with the option to replan if validation or a step fails.

Control flows within a plan map directly to software engineering constructs: sequential chains, parallel fan-out, if-statement routing, and for-loop step iteration. To measure planning quality in production, Huyen recommends three metrics evaluated against a dataset of (task, tool inventory) tuples: valid plan ratio, plans-per-valid-plan, and invalid tool call frequency. These metrics separate planning failures from execution failures, making loop problems diagnosable.

When Planning Adds Value — and When It Does Not

Of the four agentic design patterns — reflection, tool use, planning, and multi-agent collaboration — Andrew Ng considers planning the least mature. Reliability and predictability vary more across tasks than with reflection or tool use, and rapid improvement is expected as the research matures. This relative immaturity is an argument for applying planning conservatively: use it when the task genuinely requires runtime decomposition, and fall back to a simpler design when the steps are predictable.

The practical test: if a domain expert can enumerate the steps needed to complete a task before seeing any specific instance of it, a workflow is the right tool. If the steps depend on information that becomes available only mid-task — search results, API responses, intermediate computations — a planning loop earns its overhead. “Scrape a list of URLs” is a workflow. “Research a company and write a competitive analysis” is a planning problem, because the right sub-tasks depend on what the research uncovers.

Key Insight
Planning loops add value specifically when task decomposition cannot be specified at design time. For predictable step sequences, a simpler chaining workflow is faster, cheaper, and easier to debug.
Watch Out
Planning is the least mature of the four agentic design patterns. Applying it to tasks with predictable steps adds latency and complexity without benefit. Always verify that a fixed workflow cannot solve the problem before reaching for a planning loop.

LangGraph Implementation

The code below implements the plan → validate → execute cycle as a LangGraph StateGraph. The plan → validate edge adds a gate before any step is executed; if validation fails, the graph re-enters plan with the failure reason as context, enabling replanning. Once valid, execute_step runs one step at a time and loops back to itself until the plan is exhausted — this inner for-loop is what separates a planning agent from a single ReAct call. 

from langgraph.graph import StateGraph, END
from langchain_anthropic import ChatAnthropic
from typing import TypedDict, Literal
import json

llm = ChatAnthropic(model="claude-sonnet-5")

class PlanState(TypedDict):
    task: str
    plan: list[str]
    step_index: int
    results: list[str]
    valid: bool
    done: bool

def plan(state: PlanState) -> dict:
    context = f"\nPrevious plan was rejected. Revise it." if state["plan"] else ""
    response = llm.invoke(
        f"Decompose this task into ordered steps. Return a JSON array of strings.{context}\nTask: {state['task']}"
    )
    try:
        steps = json.loads(response.content)
    except Exception:
        steps = [response.content]
    return {"plan": steps, "step_index": 0, "results": []}

def validate(state: PlanState) -> dict:
    response = llm.invoke(
        f"Does this plan fully cover the task without missing steps? Reply 'VALID' or 'INVALID: <reason>'.\n"
        f"Task: {state['task']}\nPlan: {state['plan']}"
    )
    return {"valid": response.content.strip().startswith("VALID")}

def execute_step(state: PlanState) -> dict:
    step = state["plan"][state["step_index"]]
    result = llm.invoke(
        f"Execute this step: {step}\nContext from prior steps: {state['results']}"
    ).content
    new_index = state["step_index"] + 1
    return {
        "results": state["results"] + [result],
        "step_index": new_index,
        "done": new_index >= len(state["plan"]),
    }

def route_after_validate(state: PlanState) -> Literal["plan", "execute_step"]:
    return "plan" if not state["valid"] else "execute_step"

def route_after_execute(state: PlanState) -> Literal["execute_step", "__end__"]:
    return END if state["done"] else "execute_step"

builder = StateGraph(PlanState)
builder.add_node("plan", plan)
builder.add_node("validate", validate)
builder.add_node("execute_step", execute_step)
builder.set_entry_point("plan")
builder.add_edge("plan", "validate")
builder.add_conditional_edges("validate", route_after_validate)
builder.add_conditional_edges("execute_step", route_after_execute)

app = builder.compile()
result = app.invoke({
    "task": "Research and summarize recent advances in LLM efficiency.",
    "plan": [], "step_index": 0, "results": [], "valid": False, "done": False
})
print(f"Completed {len(result['results'])} steps.")
